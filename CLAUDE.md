# CLAUDE.md — ZX1 Retro Interface

## What this is

An Android HOME replacement for the Sony NW-ZX1 hi-res digital audio player (2013, Android 4.1 firmware). The stock Android interface is phone-shaped; this launcher replaces it with a dedicated digital-audio-player interface, and the goal is to make it the best dedicated DAP interface this hardware can carry.

**Design north star:** the interface Sony's portable-audio group might have shipped in 1999 — the MiniDisc Walkman era — re-imagined for this hardware with period conviction, not pastiche. When making any UI decision, ask: *would a 1999 Sony portable-audio industrial designer have shipped this?* Restraint over decoration, type over icons, function numbering over metaphor.

Derived from [Light Android Launcher](https://github.com/light-launcher/Light-Android-Launcher) (GPLv2). Keep the license headers in source files and the NOTICE attribution intact.

## Constraints

- **Android 4.1 compatibility is absolute.** `minSdkVersion 16`; every feature must run on the ZX1's firmware. Dependencies are allowed when they earn their place, but only ones that actually work at API 16 — verify before adding. Java 7 language level under the current toolchain (upgrading the toolchain is fine if the output still targets API 16).
- **Permissions, network access, services, background work, and broadcast receivers are all allowed** where they make the launcher better. Background work stays event-driven and battery-respecting — this is a DAP, never a standing drain. APK size is not a constraint.
- **Never fake data on the LCD.** Firmware 1.13 pushes no now-playing metadata (no broadcast, no RemoteControlClient), so the current track is *pulled*: `MediaServiceClient` polls the player's binder (~1 s, while home is resumed) and joins the world-readable Genie row. The status word/glyph show the player's real PLAY/PAUSE/STOP; with no binder data the fallback is `AudioManager.isMusicActive()` (PLAY/STOP only, never PAUSE). Every LCD line shows only values actually read; the last real track holds on the glass, but a new track whose Genie row can't be read goes dark rather than wear stale lines. The art panel shows a cover only when that track's art bytes were actually read (`AlbumArtResolver` cascade, winner logged under `ZX1AlbumArt`; the platform MediaStore albumart is the proven source on device), rendered per the Artwork Style setting — smooth dark→light two-tone at the panel's native resolution by default, four-tone Bayer dither at the chunky raster (GAMEBOY), or untouched full color — always in the active style's tones; with no readable cover the generated two-tone plasma runs — never an empty frame, never a placeholder, never another track's art.
- **Only documented Sony binder transaction codes are ever issued** — codes come from the decompiled client jar, never guessed against the live player.
- Portrait only, tuned for the ZX1's 480 × 854 panel — of which the app window is only **480 × 782**: the firmware keeps Android's on-screen nav bar (72 px), and `FLAG_FULLSCREEN` cannot remove it on 4.1. The LCD zone flexes (`layout_weight=1`, `minHeight 238dp`) and, inside it, the flexible element is one frame holding the art panel — or, while the music is out of reach, the storage panel — so the text lines, soft-keys, and latch always fit exactly. Chassis rows are fixed-height and the glass runs edge to edge (no chassis side bands).

On LCD every tint helper is a no-op — the proven XML resources are never rebuilt; API 16 drawables can't take theme attributes, hence runtime re-tinting. Also owns the resume-time reconciliation every screen calls (`restyleIfChanged`): the re-inflate is **posted**, never called inline from `onResume` — an inline `recreate()` there relaunches into an activity the framework pauses again the instant it has resumed, leaving the screen visible and touchable but frozen with every timer, poll and receiver torn down (findings "recreate() from onResume"). The frame is a `LayerDrawable` subclass that reports **no** padding: `setBackground` adopts a background's padding as the view's own and `LayerDrawable.getPadding` always claims to have some, which silently zeroed the glass inset every layout asks for — only in TUBE, because inflate applies `android:padding*` after the background but `applySkin()` runs later (findings "setBackground takes the view's padding with it"). Flat TUBE colors go through `Skin.paint` (a fresh `ColorDrawable`), never `setBackgroundColor`: on API 16 that writes into the inflated drawable's state without `mutate()`, and when that drawable is the one `Resources` caches for the color, every later inflation — LCD screens included — copies the tube color (findings "setBackgroundColor re-colors later inflations"). |
| [TransportGlyphView.java](app/src/main/java/com/github/postapczuk/lalauncher/TransportGlyphView.java) | The title-line transport glyph. PLAY/STOP stay the proven font glyphs (`▶`/`■`); PAUSE keeps `■` as an invisible metrics donor and draws two solid ink rectangles in its box — same baseline and advance, no font-coverage gamble. |
| [GearView.java](app/src/main/java/com/github/postapczuk/lalauncher/GearView.java) | The drawn settings gear (ring + eight square-cut teeth) — the interface's one sanctioned icon; U+2699 is unreliable in the firmware's fonts. |
| [SonyWalkmanContract.java](app/src/main/java/com/github/postapczuk/lalauncher/SonyWalkmanContract.java) | Every Sony firmware package/activity/service/action name, binder descriptor, transaction code, PlayState ordinal, Genie URI/column/projection, codec enum, and list tag. Device-specific strings go here, never inline elsewhere. |

Launch philosophy: try the exact Sony component first, then known package names, then generic Android intents. Every action must degrade gracefully off-device (`launch()` catches `ActivityNotFoundException` and reports "NOT AVAILABLE").

## Sony NW-ZX1 firmware facts (firmware 1.13)

- Player package: `com.sony.walkman.mediaplayers.wm2`; main activity `…mediaapp.music.activity.MusicTopActivity`; transport via `…music.ctrl.MusicControlService` app-widget actions; exported UI actions `ACTION_START_TOP` / `ACTION_START_DASHBOARD` / `ACTION_START_PLAYING_VIEW`. No standalone playlist action exists (the launcher's own PLAYLISTS screen replaced the dashboard delegate). Sound Enhancement: `com.sonyericsson.soundenhancement`.
- **Now-playing binder (read side):** bind `com.sony.walkman.media.IMediaService`, descriptor `…IMediaServiceRemote` — `getPlayers()` txn 3, `getPlayerInterface(name, null)` txn 1 → `…IPlayerRemote` — `getCurrentInfo()` txn 27 → PlayInfo parcel (trackId, playTime, duration, indices, PlayState `CLOSE=0/PAUSE=1/PLAY=2`). Zero permissions needed.
- **Binder write side (working):** from a **registered client only** — `getPlayerInterface(name, Bundle)` returns a client id, `addListener` txn 1 attaches a hosted `IPlayerEventListenerRemote` stub (callbacks are **not oneway**: reply instantly, never block), `setServerKeepAlive` txn 46. Then `open(PlayListSelectionInfo, true)` txn 3 + `playWithParam(PlaySpeed(1,1), false, -1)` txn 7 — never bare `play()` txn 6 (its task fails, and a failing task closes the list). Queues ride the **platform MediaStore**: Genie nulls `_data` behind signature-level `ACCESS_DRM_METADATA` and the engine resolves the queue under the submitting caller's identity, so Genie descriptors die at play. The selection *string* is writable; selectionArgs must always be written absent; ORDER BY is single-column. RequestResult's MediaError is task **submission** only — completion arrives at the listener (`onOpen`); `getMediaListInfo()` txn 22 is the read-only oracle. A shape the service dislikes **blocks forever instead of erroring** and wedges its write path until reboot (findings "The open() wedge"). Intent fallback: exported `ScanAndPlayFileActivity` (VIEW, **file scheme only**, audio mime).
- **Genie provider** (`content://com.sony.walkman.providers.GenieMediaStore/external/audio/…`, world-readable): caller WHERE selections return nothing — address single rows by appended-id URI; null projections return only `_id` — always name columns; directory reads work with explicit projections, but return nothing while Sony's rescan runs (every power-on and USB disconnect) — treat empty as unknown, not as changed.
- **USB mass storage:** the only USB function is `mass_storage,adb` (no MTP). Plugging the cable in makes Sony's Automount app (`com.sony.walkman.automount`) share the one music volume, so Android unmounts it and the player cannot play. The forced unmount kills any process still holding a file open on the volume. The stock way out, SystemUI's `UsbStorageActivity`, is not exported, but `MOUNT_UNMOUNT_FILESYSTEMS` is protection level *dangerous* on this firmware, so the launcher ends sharing itself with the hidden `StorageManager.disableUsbMassStorage()`. `MEDIA_UNSHARED` is hidden in the SDK but sent. Broadcast order, timings and Sony's reindex: findings "USB mass storage".
- Full protocol detail, parcel layouts, column catalog, quirks, and measured device facts: [docs/firmware-findings.md](docs/firmware-findings.md).

## Design language

Two zones: an STN-LCD "screen" set into a graphite "chassis". Two styles (Settings > Style) share that structure:

**LCD** (default — these are the inflate-time resources):

|---|---|---|
| `chassis_black` / `chassis_mid` / `chassis_edge` | `#0C0F0E` / `#181D1B` / `#3B423E` | Graphite body, control fills, bezels |
| `panel_white` / `panel_dim` | `#E4E6E1` / `#858C87` | Printed chassis lettering (bright / secondary) |
| `accent_orange` | `#D86A35` | The one accent. Use sparingly (currently: one footer label). |

| `lcd_search_field` | `#9AA58F` | Recessed search-field fill |

|---|---|---|

Rules:

- **Typography:** `monospace` = anything on the LCD; `sans-serif-condensed` = anything printed on the chassis. Both bold, always uppercase. (`android:fontFamily` is API 16+.)
- **No icons — one sanctioned exception.** Text and glyphs only: `▶ ■ ▲ ▼ •`, plus the drawn pause rectangles and the drawn settings gear on the program index header (`GearView`; font symbols like U+2699 are unreliable on this firmware — draw, don't gamble).
- **Nothing on screen duplicates a hardware key**: no on-screen transport, no volume. The ZX1's physical side keys own play/pause/skip/volume/hold. Home touch normally does exactly three things — MUSIC LIBRARY, PLAYLISTS (unnumbered stroked soft-keys), and the in-glass PROGRAM INDEX latch. The one exception is the storage panel's USB STORAGE state (below): there the glass carries USB STORAGE OFF and the two soft-keys are gone. Numbering lives in the program index, on library and playlist track rows, on playlist rows, and on the settings rows. An album track row carries its own tag number (`04`), never its position in the list; the one variant is a multi-disc album, whose rows read disc-first (`1-01`, `3-15`) because the same number appears on every disc of a set — type, no marker glyph, and only when the disc numbers were really read.
- The transport state is a single glyph at the end of the LCD title line; the status word (`PLAY`/`PAUSE`/`STOP`) must always agree with it (`▶` / two drawn bars / `■` — `TransportGlyphView`).
- Pressed states invert LCD ink/surface (`lcd_soft_key`, `lcd_latch`, `res/color/` selectors); controls swap instantly — no transition animation. The **three sanctioned animations**: the art panel's Bayer-dithered two-tone plasma (25 fps, only while resumed, the art panel is on the glass, and no real cover holds it), the title line's back-and-forth glide (vsync-driven, hold at each end, only while the screen is on and the track lines are on the glass), and the chassis spectrum window's envelope replay (12 fps, only while PLAY with real analysis for the position). Everything else stays static, the storage panel included.
- The chassis **info window** (top-right) is the spectrum window by default, live the honest way: each track analyzed once offline (lowest-priority service, first play) into a stored 8-band envelope, replayed by `SpectrumController` against the player's own clock — the same architecture Sony's visualizer uses. Live `Visualizer` capture is **proven impossible on this hardware** (the S-Master path delivers zeros on every format; the output mix refuses to initialize — firmware-findings.md) — do not re-propose it, and never animate the window with fake data: bars move only while PLAY with the frame's real analysis present; PAUSE/STOP, unanalyzed positions, and unreadable files hold the designed flat baseline. The analyzer decodes every library format: ALAC and >48 kHz FLAC run through the launcher's own spec-written decoders (`AlacDecoder`/`FlacDecoder`, bit-exact-verified; only genuinely broken files keep the permanent baseline). Settings > Info Screen can instead give the window to the **CLOCK**: the same rectangle re-cut in the screen colors (glass fill, ink digits), showing the real time from the existing 30 s tick — no blinking colon, nothing animated. CLOCK also turns the analysis pipeline off wholesale (device-verified): home stops requesting, a running pass yields at its next block (`yield … (spectrum off)`, partial kept), the service refuses stragglers without marking anything failed, and flipping back to SPECTRUM re-requests the playing track and resumes from the stored frame.
- The **storage panel** (`StoragePanel`, one layout for every screen) takes over wherever the music volume is out of reach, because nothing else there can be honest or useful. Home re-cuts its glass in place, the way CLOCK re-cuts the info window: the status row and the PROGRAM INDEX latch stay; the track lines, art panel and soft-keys give way. The library and playlists put it up as an opaque overlay that back leaves. Three states, all static type: **USB STORAGE** (`CONNECTED TO COMPUTER` / `MUSIC UNAVAILABLE`, with the USB STORAGE OFF key — the panel's only control and the only state that has it; it reads `NOT AVAILABLE` if the firmware refuses), **READING STORAGE** (`SONY DATABASE UPDATING` while Sony reindexes after USB storage ends — no bar), and **UPDATING LIBRARY** (the launcher's own rebuild, with a bar and `done / total` count from real row counts). The storage phases READING and UPDATING follow only a USB session; power-on rescans stay silent. (The library's nothing-cached first build reuses the UPDATING readout for its own progress.)
- Brand sublabel: `PORTABLE AUDIO SYSTEM / 2014` — the device's own year; 1999 is the design language, not a printed date.
- Interaction sounds like hardware: full-screen lists slide up over home (`R.anim.slide_up` / `slide_down`), like a mechanism, not a page.

## Build and verify

```sh
./gradlew lintDebug assembleDebug
```

That single command is the whole check gate — lint has `abortOnError true` (with `MissingTranslation` and `ExpiredTargetSdkVersion` disabled; this is a sideload-only API 16 app). Output: `app/build/outputs/apk/debug/zx1-retro-interface-debug.apk`. `scripts/build-debug.sh` wraps the gate and prints the APK path.

Toolchain: Gradle 6.9.4 wrapper, AGP 4.2.2, compileSdk 30, build-tools 30.0.3, target 28. Gradle 6.9.4 needs a JDK between 8 and 15 — do not upgrade the JDK without upgrading Gradle. `local.properties` (gitignored) points `sdk.dir` at an Android SDK with platform 30 and build-tools 30.0.3.

Expected compile noise: javac warns that source/target 7 is obsolete. Inherent to the API 16 constraint; ignore.

## Device testing

Claude builds; **the maintainer installs and tests on the physical ZX1** (`adb install -r …`). There is no emulator and no test suite — Sony intent/binder behavior can only be confirmed on the device, so state clearly when a change needs on-device verification.

## Releases

- APKs ship as GitHub release artifacts only — `*.apk` never enters git.
- Release builds are signed via an untracked `keystore.properties` in the repo root (`storeFile` / `storePassword` / `keyAlias` / `keyPassword` pointing at a keystore kept outside the repo). Without it, release builds are unsigned. Signing material is never committed.
- `scripts/`: [build-debug.sh](scripts/build-debug.sh) (the check gate), [build-release.sh](scripts/build-release.sh) (signed release into `dist/`, prints the signing certificate and sha256), [bump-version.sh](scripts/bump-version.sh) (updates `versionName`, auto-increments `versionCode`), [publish-release.sh](scripts/publish-release.sh) (tags `v<versionName>` and attaches the APK via `gh`; requires a clean tree, a pushed HEAD, and the active gh account owning the repo).
- Release flow: `scripts/bump-version.sh X.Y` → commit → push → `scripts/publish-release.sh`.

## Naming and identity

- User-visible name: **ZX1 Retro Interface** (`app_name`). Do not use "MiniDisc" in user-facing names or docs (trademark caution) — it is design inspiration only.
- `applicationId`: `io.github.justfunstuff.zx1retro`. Changing it makes Android treat the app as a different launcher — don't.
- Java package: `com.github.postapczuk.lalauncher`, kept from upstream. Leave it.
- Versioning: `scripts/bump-version.sh <versionName>` per release — it updates both fields in [app/build.gradle](app/build.gradle).
